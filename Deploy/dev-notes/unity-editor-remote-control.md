The user keeps the Unity editor open on `C:\Users\Lenovo\VR`, so `-batchmode` is blocked by the project lock. What works instead:

- **Recompile / import:** Unity only refreshes when its window gets focus. Bring it forward from PowerShell (`keybd_event` ALT tap, `ShowWindow` 6 then 9, `SetForegroundWindow` on the Unity.exe whose command line has `-createproject`/`-projectpath C:\Users\Lenovo\VR`). Wait until `Library/ScriptAssemblies/Assembly-CSharp(-Editor).dll` is newer than the edited `.cs` before doing anything else.
- **Run editor actions:** `Assets/MOI/Scripts/Editor/MoiEditorCommands.cs` polls `Temp/moi-command.txt`. Accepted: `configure`, `build-scene`, `build-apk`, `capture-stills`. Write the file only *after* the recompile finished, otherwise the old assembly eats the command.
- **See the result:** `capture-stills` enters play mode, seeks through the journey and writes PNGs to `Review/`; read those rather than screen-grabbing.
- **Log:** `%LOCALAPPDATA%\Unity\Editor\Editor.log` (directory listing shows a stale size; read the file contents). Shared with other Unity instances the user may have open (e.g. `C:\Dev\greens-mvp\HexTD`).
- **Offline compile check:** Unity's bundled Roslyn (`Editor/Data/NetCoreRuntime/dotnet.exe` + `DotNetSdkRoslyn/csc.dll`) against `Editor/Data/Managed/UnityEngine/*.dll` and `Library/ScriptAssemblies` catches C# errors before bothering the editor.

Gotcha learnt the hard way: `Mathf.SmoothStep(a, b, t)` is a lerp, not GLSL smoothstep; and `Resources.GetBuiltinResource<Mesh>("Cylinder.fbx")` rendered about twice as wide as expected here, so podium meshes are generated by `ProcMesh` instead.

**VIVE OpenXR package must stay embedded** (`Packages/com.htc.upm.vive.openxr`, real binaries pulled with `git lfs pull`). As a Unity git dependency its `.aar`/`.so` arrive as 135-byte Git LFS pointers: editor compiles fine, Gradle fails with `openxr_loader.aar: zip END header not found`. First successful APK: 2026-09-21, `Builds/MOI_PromiseOfSafety.apk` (81 MB), never yet run on a headset.

**Station intro gotcha (2026-09-27, measured on screen from the press):** WPF MediaElement on this laptop: the FIRST play of a freshly opened video shows frame 1 then freezes for seconds while audio runs (every file); a second Play of a loaded video is smooth. Fix in visitor-station.ps1: intro opened once and kept loaded; `Start-WarmUp` plays it muted for ~1.5 s after MediaOpened under an opaque black `$cover` Rectangle, then Stop; re-run at every "Waiting". Warm-up with Visibility Hidden / Opacity 0 does NOT work (must be drawn, just covered). Also never Stop/Pause/Position an unloaded player (command is kept for the next open). The station's old Position-based "longest freeze" meter measured the audio clock and missed the frozen picture - measure pixels (scratchpad station_presses.ps1 / plain_starts.ps1). Side effect: intro.mp4 is locked while the station runs.
